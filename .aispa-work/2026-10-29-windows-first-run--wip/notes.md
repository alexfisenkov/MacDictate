# Windows first-run exploration

Scope: read-only review of `windows/CLAUDE.md`, Windows source/tests/scripts, `web-landing/index.html`, and `.github/workflows/desktop-release.yml`. No project code, git state, user logs, local credentials, or hosted CI touched. This is source inspection; no Windows physical-device behavior was observed.

## Product and first-run path

- `windows/CLAUDE.md` is the local Windows contract: portable logic in `src/MacDictate.Core/`; Win32/tray integration in `src/MacDictate.Windows/`. Explicit default says double left Alt starts and another double left Alt stops; right Alt/AltGr and combos must not trigger; hook passes keys onward.
- `TrayApplication()` reads settings from `%LOCALAPPDATA%\MacDictate\settings.json` via `LocalStore`, initializes the keyboard hook, creates a notification-area icon, and calls `OpenSettings` when `ModelPath` is null or missing. There is no installer-created first-run wizard or explicit microphone permission dialog.
- The first settings screen is `SettingsForm`: language (`auto`, `ru`, `en`), hotkey (`DoubleAlt`, `CtrlShiftSpace`, `F8`), choose existing `.bin`, or “Download verified model”. Download uses pinned `runtime-lock.json` model `ggml-small.bin`, 487,601,967 bytes (~465 MiB / marketed as about 488 MB), SHA-256 check; destination `%LOCALAPPDATA%\MacDictate\models\ggml-small.bin`. User must click Save after download to persist/use `AppSettings(Language, Hotkey, ModelPath)`.
- Model download requires network access to Hugging Face. `ModelStore.DownloadAsync` streams to a `.download` temporary, caps/verifies bytes and hash, preserves an existing different file, honors cancel, then atomically moves into place. Status text reports failure. After successful download the app can recognize offline.
- `LocalStore` stores `settings.json` and `last-dictation.txt` under `%LOCALAPPDATA%\MacDictate`; load errors fall back to defaults. Settings/last text writes use temp + replace. Last transcript persists until replaced/cleared; tray menu can show/copy it or clear it.
- No explicit microphone permission request exists. `WaveRecorder.Check` error message directs user to Windows 10 Privacy > Microphone or Windows 11 Privacy & security > Microphone and choose a default input in Sound. This happens only when waveIn APIs fail, not as a clear advance onboarding step.
- `NotifyIcon` displays icon/status; recording changes icon to warning and status “Recording — double Alt stops (max 2 min)”; recognition status is “Recognizing locally…”. There is no visible main window. Tray context menu exposes Start recording/Stop and recognize, Cancel, status, Settings/download model, Show/copy last dictation, Clear saved dictation, About/releases, Quit. Tray double-click opens Settings.

## Hotkey, capture, recognition, paste contracts

- Core `HotkeyPolicy.Process(int key, bool pressed, bool injected, long milliseconds, bool recording)` recognizes only clean standalone Alt keys (`0x12`, `0xA4`, `0xA5` but rejects right Alt `0xA5`), duration <=300 ms, double tap <=400 ms. Injection, repeats, chords, held modifiers invalidate. `recording` is currently an unused parameter; caller's `ToggleAsync` decides start/stop from `recorder != null`.
- `KeyboardService.Configure(string value)` installs `WH_KEYBOARD_LL` (`SetWindowsHookEx(13,...)`) for `DoubleAlt`, or `RegisterHotKey` for alternatives. `CtrlShiftSpace` is modifier `0x4006` + VK `0x20`; `F8` is `0x4000` + VK `0x77`. Hook always calls `CallNextHookEx`. Install/registration errors are surfaced in a warning message by `TrayApplication`.
- Potential user-facing ambiguity in source/UI: SettingsForm explanatory copy says “Double left Alt starts; double left Alt again stops. Ctrl+Shift+Space and F8 toggle recording.” Web copy says left Alt twice starts and “repeat double press” stops. A user who interprets “one Alt to stop” will leave recording active until another double tap or 2-minute timer.
- Recording starts only when `settings.ModelPath` exists; otherwise Alt action opens Settings. `ToggleAsync` captures `FocusIdentity` (may be null), then creates `WaveRecorder` and starts 2-minute maximum timer. Menu action is always an alternative start/stop route.
- `WaveRecorder` uses WinMM `waveIn*`, default device (`uint.MaxValue`), mono 16kHz PCM16; writes WAV to system temp `macdictate-audio-<guid>.wav`; minimum 1600 bytes (~50ms), maximum 120s. API/capture errors include microphone settings guidance. It deletes audio after recognition/cancel/error cleanup; forced process termination can leave WAV (documented).
- Stop dismisses an active Alt menu only if target still foreground and no modifier held, then runs `WhisperRunner(Program.RuntimePath).TranscribeAsync(audio, model, language, token)`. Runtime is `AppContext.BaseDirectory/runtime/whisper-cli.exe`, timeout 5 minutes. Failures include missing runtime/audio/model, unsupported language, process nonzero exit, timeout, no text file, blank/no speech; user-visible through warning dialog.
- `FocusIdentity.CaptureAsync` requires foreground window, native focused input HWND, keyboard focusable UIA element with RuntimeId; UIA call has 500ms limit and single concurrent slot. Any mismatch/unknown identity produces null. `PasteService.TryPasteAsync` rechecks identity/foreground/menu/modifiers before and during Unicode SendInput chunks; it can return false without losing text. Fallback tray balloon says use Show/copy last dictation. Thus a recording can succeed while automatic insertion fails.
- App concurrency guards: `busy`, `modal`, `shuttingDown`; cancel stops active recorder or cancels recognition; quit waits for cleanup/message loop. Transcription saved in memory before disk write; save failure balloon advises copy before quit.

## Test and build evidence/interfaces

On Windows it runs the test apphost as fake Whisper; on non-Windows it uses shell fixture. It does not exercise real Win32 keyboard hook, microphone, tray UX, permission UX, or paste into real apps.
- Windows project build command from `windows/`: `dotnet build src/MacDictate.Windows/MacDictate.Windows.csproj`; Windows native smoke requires interactive Windows desktop. No tests were run in this exploration.

Current first-run UI opens Settings automatically, but permission instructions are absent until a capture error.

## Confirmed vs unproven

- Confirmed by source: startup auto-opens Settings when model missing; no explicit permission popup; exact tray/hotkey/model path and storage semantics above; code has explicit microphone error guidance and text/paste fallback; portable tests cover core logic.
- Not confirmed: install/run on consumer Windows 10/11, SmartScreen outcome, actual Windows privacy toggle behavior, default-microphone availability, Alt hook reliability under elevated apps/remote desktop/keyboard utilities, UI Automation identity across target apps, actual paste acceptance, full first-run usability. CI smoke and cross-build cannot establish those.
- “Alt does nothing” cause is undetermined. Source possibilities to investigate on a real machine: settings modal is open / model not downloaded or not saved / configured hotkey differs / hook installation failed (should show warning) / Windows or another hook environment / Alt press classified as chord or right Alt / recording starts but microphone setup fails / focus identity is unavailable so paste fails (should leave last text + balloon). These are hypotheses only; none identifies the user's cause.

## Open UX gaps suggested by source

- First run asks the user to infer what to do in Settings, download ~488MB, then Save; there is no explicit progress-oriented guided checklist, model prerequisite attached to the tray state, or microphone permission walkthrough before first capture.
- Tray-only surface can be mistaken for a non-running app; no persistent onboarding window explains how to find tray icon, exact double-tap cadence, recording state, max duration, or stop behavior.
- Current Alt wording is easy to misread; align landing and app instructions and make status/stop action unambiguous.
- Error messages exist for many technical failures, but there is no explicit recovery path grouped by “microphone”, “hotkey”, “model/network”, “text not inserted”.
- Next validation should use a real supported Windows 10/11 desktop and record exact results for first launch, download/save, privacy settings, default mic, double-Alt start/stop, tray status, recognition, paste to ordinary/elevated/focus-changing apps, cancel, and offline post-download run. Do not infer that result from Server 2025 CI.
